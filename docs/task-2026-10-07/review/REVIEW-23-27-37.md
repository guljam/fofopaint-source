# 연출 길이 10초 제한 / packStamp 검토 (2026-10-07, 기준 커밋 801e2b5)

대상: `ReplayState.stampTimingSheetToolCommand`, `TimingSheetFile.packStamp/unpack*`, 사용처(FillPenTool, LassoTool, MoveTool, LineTool), 재생 쪽(ReplayClock, ReplayDrawer.prepareFrameAnim, ReplayAnim)
방식: 정적 리뷰만 했음 (코드 수정 없음)

---

## 1. 10초 제한(ANIM_COMMAND_TIME_LIMIT_MS)은 맞는 동작인가

**목적에는 맞고, 넣는 위치(녹화 시점)도 맞음.** 다만 아래 부작용이 있으니 의도한 것인지 확인이 필요함.

### 재생에서 실제로 어떻게 되는가
- 명령의 시각은 도구를 시작한 시각이고, 다음 명령과의 간격(delta)은 실제로 걸린 시간 전체임. 10초로 줄이는 것은 **연출 길이만**이고 간격은 그대로임
- 재생할 때 쉬는 구간은 `시작 시각 + 연출 길이`부터 계산함 (ReplayClock.as:111, 134, 549)
- 그래서 도구를 오래 쓰면 `실제 사용 시간 - 10초`만큼이 **쉬는 구간**으로 바뀜. 시크바 축과 재생 대기가 같은 규칙을 써서 서로 어긋나지는 않음

예시 (1배속, ENTRY_MS 6초, CAP_MS 5초):

| 도구 사용 시간 | 재생 |
|---|---|
| 8초 | 8초 연출 |
| 14초 | 10초 연출 → 4초 동안 아무 변화 없음 (쉬는 구간 기준인 6초보다 짧아서 그냥 기다림) |
| 60초 | 10초 연출 → Replay Waiting(AFK 상자/커서 연출) 5초 → 건너뜀 |

- 이 제한이 없으면 60초짜리 연출을 다 봐야 했으므로 의도대로 동작함
- **확인할 점**: 연출 직후에 AFK 표시가 나오는 것(60초 예시)이 원하는 모습인지

### 문제점
1. **line4(선 도구)의 점별 시각이 같이 줄지 않음** — `pointStamps`는 도구 시작 기준 실제 ms 그대로 저장되는데(ReplayState.as:134), 재생할 때 `recorded[i] > totalMs`이면 기록된 시각을 버림(ReplayAnim.as:243). 그래서 10초 넘게 그린 선은 점별 시각을 잃고 경로 길이 비례 방식으로 바뀜. 질문에서는 fill/move/lasso만 말했지만 line4도 같은 함수를 지나감
   - 해결 방향: 점 시각에도 같은 제한을 적용 (`min(값, 10000)`, 마지막 점들이 10초에 몰림) 또는 `10000 / 실제 길이` 비율로 줄이기
2. **변수 이름이 맞지 않음** — `endStamp`는 끝난 시각이 아니라 걸린 시간(연출 길이)임. `animMs`가 맞음
3. **이미 저장된 데이터에는 적용되지 않음** — b4d6127 이전에 녹화한 파일의 연출 길이는 10초를 넘을 수 있음(최대 MAX_ANIM_MS). 옛 파일에도 제한을 적용하려면 재생 쪽(`ReplayClock.animMsOfFrame` 또는 `prepareFrameAnim`)에서도 줄여야 함. 단, 그러면 쉬는 구간 계산(ReplayClock.as:111/134/549)도 같은 값을 써야 시크바와 맞음

## 2. MAX_ANIM_MS를 10000으로 두면 되는가 — 두 값은 의미가 다름

| | ANIM_COMMAND_TIME_LIMIT_MS (10000) | MAX_ANIM_MS (2097151) |
|---|---|---|
| 종류 | 정책: 연출을 얼마나 길게 보여줄지 | 저장 형식의 한계: 합친 Number가 정확한 정수(2^53 미만)로 남도록 하는 비트 폭(21비트) |
| 바뀌는 이유 | 기획 결정 | 저장 형식이 바뀔 때만 |

- MAX_ANIM_MS를 10000으로 바꿔도 동작은 같아짐 (packStamp가 잘라냄)
- 하지만 **권장하지 않음**: "얼마나 길게 보여줄지"라는 결정이 형식 함수 안에 숨고, 나중에 제한을 15초로 바꿀 때 형식 상수를 건드려야 함
- 지금처럼 녹화 시점에 정책으로 자르고, MAX_ANIM_MS는 형식을 지키는 마지막 안전장치로 두는 것이 맞음

## 3. 왜 Number 하나로 합치는가 (과설계인가)

### 합친 이유 (6b0edcd에서 연출 길이를 추가할 때의 선택으로 보임)
- 원래 `rMemoryDataTimingSheet`는 **명령마다 getTimer 값(숫자) 하나**인 배열이었음
- `packStamp(stamp, 0) === stamp`라서, 연출 길이가 0인 명령(펜 lineTo 등 대부분)의 값은 예전과 똑같음
  - 예전 undo 저장 파일(AppStateManager.as:945 `writeObject`)을 그대로 읽을 수 있음
  - splice/pop/shift/push 하는 곳 10여 군데(ReplayState, UndoHistory, ReplayController)를 고치지 않아도 됨
  - 명령마다 배열 객체를 새로 만들지 않아서 메모리와 AMF 크기가 늘지 않음

### 그래도 과설계라는 지적은 일리가 있음
- 이미 line4는 `[packed, points]` 배열로 저장해서 "숫자 하나" 모양이 지켜지지 않고 있음. 모든 읽는 곳은 `packedOf/pointsOf`를 거침
- 같은 효과를 비트 연산 없이 낼 수 있음: **연출이 없으면 숫자 그대로, 있으면 `[stamp, animMs, points]` 배열**
  - 예전 데이터와 맞고, 연출 명령은 드물어서 배열이 늘어나는 비용도 거의 없음
- "시작 시각과 끝 시각을 따로 저장해서 차이를 쓰자"는 방식도 가능함. 단, 그러면 10초 제한을 읽을 때마다 적용해야 하고, 앱을 다시 켤 때 시각을 옮기는 `shiftElement`가 두 값을 모두 옮겨야 함. 지금처럼 길이를 저장하는 쪽이 조금 더 단순함

### 판단
- 지금 코드는 **틀린 곳은 없음**. 고칠지 말지는 취향 문제에 가까움
- 바꾼다면 배열 방식이 더 읽기 쉬움. 다만 저장 형식이 바뀌므로 예전 undo 파일 읽기(숫자 = 연출 0)와 하네스 등가성 테스트가 필요함

## 4. Number의 가수부 52비트 안에 int 2개를 넣어도 되는가 — 문제 없음

- AS3 Number는 IEEE 754 double임. 저장되는 가수부는 52비트지만 숨은 1비트가 있어서 **2^53까지의 정수는 정확히** 표현됨
- 여기서 합치는 것은 int 두 개(64비트)가 아님
  - 아래 32비트: `uint(stamp)`
  - 위 21비트: animMs, MAX_ANIM_MS = 2^21 - 1로 제한됨
  - 합계 53비트이고 최댓값 = (2^21 - 1)·2^32 + (2^32 - 1) = 2^53 - 1이므로 정확한 범위 안에 들어감
- 풀 때 `% 2^32`, `/ 2^32` 후 `floor`를 쓰는데, 2의 거듭제곱으로 나누는 것이고 값이 정확한 정수라서 반올림 오차가 없음
- 음수 stamp(shiftElement에서 offset 때문에 생길 수 있음)도 `uint()`로 넣고 `int(uint())`로 되돌려서 그대로 복원됨
- 10초 제한이 생겨서 animMs는 14비트면 충분하므로 여유가 더 큼
- 참고: AMF3에서 stamp < 2^28이고 연출이 0이면 int(1~4바이트)로, 연출이 있으면 double(8바이트)로 저장됨. 크기 차이는 무시할 만함
